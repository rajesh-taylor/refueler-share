# ONBOARDING-RUNBOOK.md — Refueler Share API
> Version: 1.0 | Created: SW7 · 10 Sep 2026
> Sanitised template — no client names, no prices, no AM name, no live secrets.
> Per-client instances are off-repo. All `{tokens}` are resolved at activation.

---

## Overview

This runbook takes a new API client from signed agreement to activated credentials.
Every step is linear and resumable. Steps marked **[IDENTITY]** or **[ANON]**
apply to that rail only. Unmarked steps apply to both.

Security rests on secrets and credential-type separation — not on this procedure
being hidden. It is safe to commit sanitised.

---

## Step 1 — Custom hostname (identity-rail white-label only) [IDENTITY]

Add the client's chosen hostname to `wl_config.js` in `refueler-share/worker/src/`.
Find `WL_CONFIGS` and add an entry for `{custom_hostname}`.

Trigger CF for SaaS ownership challenge:

```
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/{CF_ZONE_ID}/custom_hostnames" -H "Authorization: Bearer {CF_SAAS_TOKEN}" -H "Content-Type: application/json" -d "{\"hostname\":\"{custom_hostname}\",\"ssl\":{\"method\":\"http\",\"type\":\"dv\",\"settings\":{\"min_tls_version\":\"1.2\"}}}"
```

Expected: `"status":"pending"`. SSL provision takes 2–15 minutes.
Failure mode: `"code":1414` = hostname already claimed by another zone. Client must CNAME before retry.

## Step 2 — Generate production keypair

Keypair is generated by the Worker's `/api/v1/credential/issue` endpoint using
`crypto.getRandomValues()`. Never derive from `rfs_test_` credentials.
Never copy from sandbox output.

```
curl -s -X POST "https://api.share.refueler.io/api/v1/credential/issue" -H "X-Admin-Key: {ADMIN_KEY}" -H "Content-Type: application/json" -d "{\"rail\":\"{rail}\",\"client_ref\":\"{client_ref}\",\"plan\":\"api\"}"
```

Expected response shape:
```json
{
  "live_key": "rfs_live_...",
  "sign_key": "rfs_sign_...",
  "whsec_key": "rfs_whsec_...",
  "rail": "identity|anonymous",
  "client_ref": "{client_ref}",
  "created_at": 1234567890
}
```

**Capture output to a local variable only. Do not log it. Do not email it.**
`rfs_whsec_` is API-tier only; absent for any other tier.

## Step 3 — Write client record to KV

```
curl -s -X PUT "https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/storage/kv/namespaces/{KV_NAMESPACE_ID}/values/api_client_{client_ref}" -H "Authorization: Bearer {CF_API_TOKEN}" -H "Content-Type: application/json" -d "{\"rail\":\"{rail}\",\"plan\":\"api\",\"active\":true,\"created_at\":{created_at},\"custom_hostname\":\"{custom_hostname}\"}"
```

**[IDENTITY]** Include `"rail":"identity"` explicitly — this field gates v2 feature access.
**[ANON]** No Supabase row. No email field. KV write only. Confirm no email address
has been collected at any point in the activation flow before proceeding.

Expected: HTTP 200, `{"success":true}`.
Failure mode: 401 = wrong CF API token scope. Needs `Workers KV Storage:Edit`.

---

## Step 4 — Register webhook endpoint (API tier only)

Client must provide an HTTPS webhook URL (no localhost, no private IP ranges).

```
curl -s -X POST "https://api.share.refueler.io/api/v1/webhook/register" -H "X-Api-Key: {live_key}" -H "X-Api-Sign-Key: {sign_key}" -H "Content-Type: application/json" -d "{\"url\":\"{webhook_url}\"}"
```

Expected: `{"registered":true,"url":"{webhook_url}"}`.
`rfs_whsec_` is derived statelessly from `WEBHOOK_SIGNING_MASTER_KEY` — it is never
stored. Client receives it once via the dashboard (Step 5) and must store it immediately.

## Step 5 — Credential delivery

**[IDENTITY]** Physical envelope only. Print the credential page (see §Physical delivery
template), wax seal, company stationery envelope, hand-deliver or arrange secure courier.
No email, no Slack, no shared doc.

**[ANON]** Client self-provisions from the authenticated dashboard after completing
sandbox validation. AM does not handle the live signing key. (v1: AM provides
`rfs_live_` only via dashboard; client generates `rfs_sign_` via dashboard flow.)
Note: full client self-provisioning from dashboard is a v2 capability.
In v1, use the physical delivery flow for all clients.

## Step 6 — Activation smoke test

Provide client with `refueler-smoke.txt` (repo root). Client uploads via their
integration. AM verifies:

```
curl -s -X GET "https://api.share.refueler.io/api/v1/receipt/{uuid}/accepted" -H "X-Api-Key: {live_key}" -H "X-Api-Sign-Key: {sign_key}"
```

Expected: acceptance receipt with `status: "accepted"`.

Client then deletes the smoke test file via owner-delete endpoint.
**[ANON]** Confirm token burned correctly. Confirm 402 fires on exhaustion with a
zero-balance test.

## § Planned capability — transition from identity rail to anonymous rail

> Status: planned. Available when Silent Drop block ships. Do not execute until SD is live.

### Summary

A client wishing to move from identity to anonymous rail does so as two separate
commercial relationships — not a settings change. The identity relationship closes;
the anonymous relationship opens. There is no straddled-rail period.

### Billing

Identity-rail billing stops on the day the transition is declared. The 60-day
wind-down window is provided at no charge as a counterparty-continuity courtesy.
Anonymous-rail billing starts from day one of the new credential. No overlap.
State this explicitly at the initial transition conversation — not on the invoice.

### Wind-down procedure (60 days)

- Day 0: client declares intent. AM records declaration. New upload quota set to zero.
  Existing transfers remain accessible (download only). SD inboxes remain open for
  inbound delivery only (no new provisioning).
- Days 1–60: client migrates counterparties to new links and advises them to
  retrieve existing documents within the window.
- Day 60: identity credentials revoked. KV record marked `active: false`.
  Stripe subscription cancelled. Final invoice issued. DPA closed. AM sends
  written confirmation of relationship closure.
- Day 61: anonymous onboarding begins as a fresh relationship with no carried
  identifier. Standard anonymous onboarding flow from Step 2 (anon path).

## § Client operational security template (anonymous rail)

> Provide this to any anonymous-rail client that does not have an existing
> documented key management procedure.

---

**API Credential Management — Minimum Requirements**

Your Refueler Share API signing key is an infrastructure secret equivalent to a
root database password. The following are minimum requirements, not suggestions.

**Storage**
Store all three credentials (`rfs_live_`, `rfs_sign_`, `rfs_whsec_`) in a secrets
manager (examples: HashiCorp Vault, AWS Secrets Manager, 1Password Teams,
Bitwarden Secrets Manager). Never in a shared document, email, or chat tool.

**Access**
At least two authorised staff members must be able to retrieve the credential.
Access is logged. Review access logs quarterly.

**Rotation procedure**
If any of the following occur, rotate immediately:
- A staff member with credential access leaves the organisation
- A device holding the credential is lost, stolen, or compromised
- You suspect the credential has been observed by an unauthorised party

To rotate:
```
curl -s -X POST "https://api.share.refueler.io/api/v1/keys/rotate" -H "X-Api-Key: {live_key}" -H "X-Api-Sign-Key: {sign_key}"
```

This opens a 24-hour grace window during which both old and new credentials are valid.
Update your secrets manager and all deployment environments within the window.

**Loss**
Loss of all copies of the signing key with no rotation window active means loss of
account. There is no recovery path. This is a deliberate architectural property of
the anonymous rail, not a support failure. Treat your credential accordingly.

## § Do-not-retry (onboarding)

- DO NOT email credentials under any circumstances
- DO NOT derive production keypair from `rfs_test_` credentials
- DO NOT add an email field or Supabase row for anonymous-rail clients
- DO NOT allow new uploads during identity-rail wind-down window
- DO NOT start the anonymous relationship before identity billing has formally stopped
- DO NOT skip the Raven canary briefing for identity-rail clients
- DO NOT perform the activation smoke test with real client cargo
- Use `api.share.refueler.io` for all activation curls — never `workers.dev`
