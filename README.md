# Refueler Share

[![Apache 2.0](https://img.shields.io/badge/licence-Apache_2.0-blue)](./LICENSE)
[![Live](https://img.shields.io/badge/live-refueler.io%2Fshare-brightgreen)](https://refueler.io/share/)

Anonymous encrypted file transfer. Server-blind. Bitcoin-native. Live at
[refueler.io/share/](https://refueler.io/share/). Files are chunked,
encrypted in the browser before any network contact, and stored as
ciphertext the Refueler Worker cannot read; access is gated by cryptographic
capability rather than accounts.

---

## Architecture

The Cloudflare Worker is a blind byte-relay. It stores ciphertext and
verifies per-chunk BLAKE3 hashes; it has no access to plaintext, no access
to the session key, and on the anonymous rail no knowledge of who sent
anything.

Files are split into chunks of up to 10 MiB and encrypted with AES-256-GCM
in the browser before upload. The session key — a raw AES-GCM key generated
locally — lives in the `share_url` URL fragment only. Fragments are never
sent to a server, never present in Worker logs, and never stored anywhere
outside the client. The Worker sees neither the key nor the plaintext.

Chunk storage is Cloudflare R2. Each chunk is stored under
`{uuid}/{0000…NNNN}` with a BLAKE3 integrity hash verified at every upload;
the Worker returns HTTP 400 on any mismatch. A sidecar object at
`{uuid}/hashes` holds the raw 32-byte BLAKE3 digest for each chunk in
upload order. Full Merkle-root verification — where the Worker reconstructs
the complete ciphertext Merkle tree from the sidecar on download and
compares it against the root committed at upload — is in build (B9) and
not yet live. The correct current claim is chunk integrity per upload, not
ciphertext storage integrity end-to-end.

Access is gated by Cashu blind-signature tokens. These are capability
atoms — not monetary units, not monetary Cashu tokens — issued by an
internal mint and presented at credential issuance. They are never melted
for satoshis; their only function is anonymous access control. On the
anonymous (Bearer) rail, the Worker cannot see who is spending a token
because that is what blind signatures are for.

For Sovereign and Chartered transfers, senders may opt into a permanent
record: a Bitcoin-anchored existence proof generated by the
OpenTimestamps protocol. The Worker relays an opaque 32-byte SHA-256
digest (never the file, never the plaintext) to the OTS calendar network.
The resulting timestamp proves that specific bytes existed on or before a
given Bitcoin block date. It does not prove authorship, truth, or delivery.

Three hashes, three jobs:

- **BLAKE3** — chunk integrity. Runs in the Worker and in the browser.
  Verifies that ciphertext was stored and served without corruption.
- **SHA-256 (OTS)** — existence proof. Client-side only, never enters the
  Worker. Produces the Bitcoin-anchored permanent record for opt-in transfers.
- **Cashu** — anonymous access control. Not a hashing layer; not a monetary
  settlement layer. Blind-signature tokens as capability atoms.

## Tiers

| Tier | Rail | Payment | Storage cap | Notes |
|---|---|---|---|---|
| Pro Bono | — | Public good | 2 GB | Free. Rate-limited. No permanent record. |
| Citizen | Registered | Stripe (GBP) | 50 GB | Identity rail. Private transfers. Permanent record opt-in. |
| Sovereign | Bearer | Lightning (sats) | 50 GB | Anonymous rail. No email. No Supabase row. Permanent record opt-in. |
| Chartered | Registered or Bearer | Stripe / invoice, or Lightning | 250 GB + overage | API and MCP access. HMAC credentials. Webhooks. |

Citizen and Sovereign are the same price and feature set — the choice is
how you wish to appear.

## MCP / API

The `@refueler/mcp-server` npm package gives an AI agent file-transfer
capability that runs entirely in the agent's own trust domain:
[github.com/rajesh-taylor/refueler-mcp](https://github.com/rajesh-taylor/refueler-mcp).
Refueler never sees your keys or your plaintext — the MCP server handles
encryption locally before anything touches the network.

## Stack

| Layer | Technology |
|---|---|
| Edge compute | Cloudflare Workers |
| Chunk storage | Cloudflare R2 |
| State / KV | Cloudflare KV (`STATUS_KV`) |
| Analytics | Cloudflare Analytics Engine |
| Chunk integrity | BLAKE3 WASM (Worker + browser local bundle) |
| Session encryption | AES-256-GCM (Web Crypto API) |
| Anonymous auth | Cashu NUT-00 / NUT-11 blind signatures |
| Existence proof | OpenTimestamps (SHA-256, client-side relay) |

## Repo layout

```
worker/src/       Cloudflare Worker — upload, download, auth, receipts,
                  webhooks, OTS relay, tiers, rate limiting
frontend/         Browser JS and CSS (canonical source)
  share.js        Entry point, DOM, mode detection
  crypto.js       AES-GCM, BLAKE3, NUT-00, SHA-256, config constants
  upload.js       Upload state machine, IDB resume, folder handling
  download.js     Download state machine, OTS offer
  timestamp.js    OTS pipeline
bin/sync-share.sh Asset sync from frontend/ to refueler-io/src/share/assets/
```

Frontend assets (`share.js`, `share.css`, `blake3/`) are canonical here
and mirrored into the `refueler-io` repo by `bin/sync-share.sh`. Never
edit the mirror directly — run the sync script after every change to a
shared asset.
